## 3. Git flow

### Ветки

- **`main`** — стабильная. Прямые пуши **запрещены**. Только через PR.
- **`develop`** — интеграционная. Сюда мёржатся все фичи.
- **`feature/xxx`** — новая функциональность
- **`fix/xxx`** — багфиксы
- **`refactor/xxx`** — рефакторинг
- **`docs/xxx`** — только документация
- **`chore/xxx`** — конфиг, деп-обновления, CI

### Формат коммитов — Conventional Commits

```
<type>(<scope>): <краткое описание в present tense, до 72 символов>

<опциональное подробное описание>

<опциональный footer: Refs #123, Breaks: xxx, Co-Authored-By>
```

**Типы:**

- `feat` — новая функция
- `fix` — багфикс
- `refactor` — рефакторинг без изменения поведения
- `docs` — только документация
- `test` — только тесты
- `chore` — конфиги, деплой, деп-обновления
- `perf` — оптимизация производительности
- `style` — форматирование (не логика)

**Примеры:**

```
feat(yandex-direct): add Campaigns.get client method with units tracking
fix(vk-ads): handle 429 with exponential backoff (was retrying instantly)
refactor(optimizer): extract rule engine into pure functions for testability
docs(tz): add section 15 on ingesting existing campaigns
```

### Pull Requests

- Один PR = одна логическая задача
- Title в стиле Conventional Commits
- Description: **зачем** делаем (не что — это в коде), ссылка на milestone/issue
- Обязательно: **тесты** для новой логики
- CI должен быть **зелёным** до мёржа
- Squash merge (никаких merge commits)

## 4. Стиль кода

### TypeScript

- **strict: true** в `tsconfig.json`
- Никаких `any` — только `unknown` с сужением типа
- Экспортировать через **named exports**, не default
- Public API функций — явные типы аргументов и возвращаемого значения

### Стиль

- **Prettier** (конфиг в `.prettierrc`)
- **ESLint** с `@typescript-eslint/recommended` + `eslint-plugin-import`
- Двойные кавычки для JSX, одинарные для JS
- Semicolons — обязательны
- 100 символов на строку

### Именование

- **PascalCase** — типы, интерфейсы, классы, компоненты
- **camelCase** — переменные, функции, методы
- **UPPER_SNAKE_CASE** — константы верхнего уровня
- **kebab-case** — имена файлов
- Файлы с реализацией одной сущности — `<name>.ts`
- Тесты — `<name>.test.ts` рядом с реализацией

### Комментарии

**По умолчанию комментариев НЕ писать.** Хорошее имя = документация.

Писать только когда:

- **Почему** сделано именно так (не что) — например, `// workaround: Yandex API returns 200 with error in body`
- Хитрое место, где следующий человек споткнётся
- Ссылка на баг/тикет с контекстом

**Что не писать:**

- Пересказ кода
- Историю разработки («раньше было так»)
- TODO без даты и автора (использовать GitHub Issues)

### JSDoc

Только для **публичного API модулей** и **сложных сигнатур** с несколькими параметрами.

```ts
/**
 * Update bid on a Yandex Direct keyword with retries and units tracking.
 *
 * @param keywordId - external Yandex Direct keyword ID
 * @param newBid - bid in kopecks (100 = 1 rub)
 * @returns updated bid, or null if rejected by API
 * @throws {UnitsExhaustedError} when daily units budget is exhausted
 */
export async function updateKeywordBid(keywordId: number, newBid: number) {...}
```

## 5. Тесты

### Правила

- **Каждая новая функция — тест ДО реализации** (TDD)
- Coverage порог: **80%** для новых модулей, **60%** для legacy
- Три уровня:
  - **Unit** — pure functions, отдельные модули
  - **Integration** — с БД (test DB через Docker) + моки внешних API
  - **E2E** — полный сценарий (только для критических флоу: approval, optimization cycle)

### Инструменты

- `vitest` — раннер
- `msw` — моки HTTP
- `@faker-js/faker` — тестовые данные
- `testcontainers` — реальный Postgres в тестах

### Никогда не мокать

- Собственную БД в интеграционных тестах (использовать тестовый Postgres)
- Zod схемы (валидация должна быть настоящей)

### Всегда мокать

- Внешние API рекламных площадок (Yandex, VK, TikTok)
- LLM-вызовы (использовать snapshot тесты)
- Telegram API

## 6. Секреты и безопасность

### Категорически запрещено

- Хардкодить токены/ключи в коде
- Коммитить `.env` в git
- Логировать полные токены (только последние 4 символа)
- Хранить креды клиентов в plain text в БД

### Обязательно

- Все секреты — через `process.env`
- Токены клиентов в БД — **зашифрованы** через AES-256-GCM (ключ шифрования — в env)
- В `.env.example` — только имена переменных, без значений
- Ротация мастер-ключа — процедура в `docs/security.md`
- Логировать доступ к креденшелам клиентов (audit log)

### При работе с API рекламных площадок

- Всегда идемпотентность через `Idempotency-Key`
- Rate limits соблюдать ДО отправки (не полагаться на 429)
- Все ошибки в `ErrorLog` с контекстом
- Circuit breaker — если 10+ ошибок за 5 минут → пауза 15 мин

## 7. Работа с БД

### Миграции

- **Только через Prisma Migrate**
- Одна миграция = одно логическое изменение
- Никогда не редактировать применённую миграцию
- Backward-compatible изменения — приоритет (добавляй колонку nullable, потом заполни, потом делай required)

### Правила

- Никаких `SELECT *` — только явные поля
- Индексы для всех WHERE/JOIN/ORDER BY колонок
- Транзакции для мультитабличных операций
- Использовать `$transaction` для гарантий

## 8. AI-агенты (специфика проекта)

### Prompt engineering

- Промпты — **отдельные файлы** в `src/ai/prompts/*.md`
- Версионирование через переменную `PROMPT_VERSION` в системе
- Все промпты — на **русском** (клиенты РФ)
- Structured output через Zod schemas + `response_format: json_schema`

### Выбор модели

Смотри рекомендации в TZ.md § 13. Общий принцип:

- **Быстрое** (классификация, извлечение) — Haiku / gpt-4o-mini
- **Диалог** (онбординг, follow-up) — Sonnet
- **Reasoning** (стратегия, конкурентный анализ) — Opus / GPT-4o
- **Массовое дешёвое** (тексты объявлений) — DeepSeek

### Оценка качества

- Каждый AI-агент имеет **eval-набор** в `tests/ai-evals/`
- CI гоняет evals на PR, показывает регрессии
- Прежде чем менять промпт — записать baseline

## 9. Логи и мониторинг

### Уровни

- `error` — что-то сломалось, требует внимания
- `warn` — что-то подозрительное, но система работает
- `info` — важные бизнес-события (оплата, новая кампания)
- `debug` — техническая детализация

### Формат

Только структурированные логи через Pino:

```ts
logger.info({ campaignId, budgetBefore, budgetAfter }, 'Budget updated');
```

Никакого `console.log`.

### Алерты в Telegram

- Все `error` уровня — в TG Роману
- `warn` — только если больше 10 за 5 минут
- Формат алерта: краткое описание + ссылка на лог (пусть даже локальный путь)

## 10. Работа с Романом

- **chat_id для sessions_send:** переменная `TELEGRAM_ADMIN_CHAT_ID`
- **Timezone:** Europe/Moscow (UTC+3), не писать в 22:00-08:00 без крайней необходимости
- **Стиль общения:** на «ты», без формальностей, без «уважаемый»
- **Ответы:** краткие, по делу, с фактами и ссылками на файлы

### Когда обязательно спрашивать

- Меняешь публичный API/схему БД (breaking change)
- Тратишь деньги (LLM API, сторонние сервисы) — оценить cost до
- Пушишь в main
- Удаляешь что-либо в БД или файловой системе
- Не понимаешь требование из ТЗ — не додумывай

### Когда НЕ спрашивать

- Форматирование, стилистические правки
- Написание тестов
- Локальные экспериментальные ветки
- Внутренние абстракции, если не меняют публичный API

## 11.1 Отчётность и уроки

Два живых документа рядом с кодом, оба обновляются по ходу работы, а не пачкой:

- [`docs/READINESS.md`](./docs/READINESS.md) — готовность к проду. **Каждая цифра
  несёт пометку источника** (`[проверено]` / `[аудит]` / `[по ТЗ]`). Исправления
  вносятся в обе стороны, и отдельный раздел ведёт список исправлений против себя:
  без него остальные цифры ничего не стоят. Единой цифры «процент готовности» там
  нет намеренно — она ниоткуда не выводится и была бы оптимизмом с видом факта.
- [`docs/LESSONS.md`](./docs/LESSONS.md) — особенности окружения, добытые дорогой
  ценой. Правило простое: если ты потратил час на то, чтобы понять, почему что-то
  зависает или врёт, — это урок, и он записывается. Неверный урок удаляется.

Отчёт, живущий только в переписке, не доставлен.

## 12. Definition of Done

Задача считается выполненной когда:

1. ✅ Код написан и локально работает
2. ✅ Unit + integration тесты покрывают новую логику
3. ✅ Все тесты зелёные (`pnpm test`)
4. ✅ Линтер и форматтер зелёные (`pnpm lint && pnpm format:check`)
5. ✅ TypeScript компилируется без ошибок (`pnpm typecheck`)
6. ✅ Обновлён `CHANGELOG.md` если меняется поведение
7. ✅ Обновлена документация если меняется API
8. ✅ Создан PR с осмысленным описанием
9. ✅ CI зелёный
10. ✅ Ревью пройдено (AI + Роман)

## 13. Быстрые команды

```bash
# Разработка
pnpm dev              # запуск с hot reload
pnpm build            # сборка prod
pnpm start            # запуск prod

# Тесты
pnpm test             # все тесты
pnpm test:unit        # только unit
pnpm test:integration # только integration (нужен Postgres)
pnpm test:watch       # watch mode

# Качество
pnpm lint             # ESLint
pnpm lint:fix         # ESLint + autofix
pnpm format           # Prettier
pnpm typecheck        # TypeScript

# БД
pnpm prisma migrate dev   # создать миграцию
pnpm prisma studio        # GUI для БД
pnpm prisma generate      # regenerate client

# Docker
docker compose up -d      # поднять postgres + redis
docker compose down       # остановить
docker compose logs -f    # логи

# Деплой
pnpm deploy               # деплой на прод (хост — в DEPLOY_HOST)
```

ads-autopilot

Спецификация взаимодействия с API Яндекс Директа v5 · приложение auto_smart_school · 8 августа 2026

1. Назначение

Серверная система автоматического управления рекламными кампаниями в Яндекс Директе. Используется для ведения собственных рекламных аккаунтов: первичная сборка структуры аккаунта и ежедневная оптимизация по данным Яндекс Метрики.

Пользовательского веб-интерфейса для сторонних рекламодателей нет. Управление — через CLI на сервере и Telegram-бота для подтверждения критичных изменений.

4. Схема взаимодействия

4.1. Первичная сборка аккаунта (разовая операция, по команде оператора)

Структура аккаунта описана в системе как типизированная конфигурация: кампании, группы, ключевые фразы, тексты объявлений, быстрые ссылки, уточнения, регионы и бюджеты. Перед отправкой конфигурация проходит локальную валидацию по лимитам Директа — длина заголовков и текстов, количество слов во фразе, число фраз в группе, дубли фраз между группами. Заведомо некорректные объекты в Директ не отправляются.

валидация конфигурации (локально, без обращений к API) ↓ campaigns.add → сохраняем CampaignIds ↓ adgroups.add → сохраняем AdGroupIds ↓ keywords.add → пакетами, до 10 000 объектов на запрос ↓ ads.add → кампании создаются остановленными ↓ sitelinks.add / adextensions.add / audiencetargets.add ↓ campaigns.get → сверка созданного с конфигурацией

Объём одного прогона — порядка 300 объектов. Кампании создаются в состоянии «остановлена»: показы включает человек после визуальной проверки.

4.2. Ежедневный цикл оптимизации (1 раз в сутки, ночью)

reports → статистика по кампаниям, группам и фразам за вчера и за 7 дней reports → отчёт по поисковым запросам ↓ правила оптимизации выполняются локально, без обращений к API ↓ keywords.update / keywords.delete — фразы без конверсий campaigns.update — перераспределение недельных бюджетов adgroups.update — минус-фразы из поисковых запросов campaigns.suspend — только после подтверждения человеком

Порядок 20–50 запросов в сутки на один рекламный аккаунт. Изменение бюджета более чем на 20% и остановка кампании не применяются автоматически: система отправляет запрос на подтверждение в Telegram и ждёт ответа оператора.

4.3. Контроль модерации (2 раза в сутки)

ads.get (FieldNames: Id, State, Status, StatusClarification) ↓ отклонённые объявления → переписывание текста → ads.update

5. Соблюдение ограничений API

  • Не более 5 одновременных запросов на рекламодателя.
  • Объекты передаются пакетами, а не по одному.
  • Остаток баллов читается из заголовка Units после каждого ответа; при приближении к суточной квоте работа останавливается до следующих суток.
  • Ошибка 56 (превышение частоты) — повтор с экспоненциальной задержкой, не более 3 попыток.
  • Ошибка 152 (исчерпание баллов) не повторяется: работа откладывается до обновления квоты.
  • Ошибки 53, 54, 58 не повторяются — требуют вмешательства оператора.
  • RequestId из заголовка ответа сохраняется в журнале ошибок для обращений в поддержку.

6. Интерфейс оператора

Проверка доступа к API и состояния аккаунта выполняется командой pnpm yd:check. Фактический вывод команды на момент подачи заявки:

$ YANDEX_DIRECT_TOKEN=*** pnpm yd:check Окружение: production Токен: ***HJ-k Доступа нет: Приложению не одобрен доступ к API. Директ → Настройки → API → заявка на доступ. RequestId: 1210628317638061436

После получения доступа та же команда выводит:

Окружение: production Токен: ***HJ-k Аккаунт: <логин> (ClientId <id>, RUB, CLIENT) Кампаний в аккаунте: 11 <id> SUSPENDED/ACCEPTED SS | Поиск | Взрослые | Петергоф <id> SUSPENDED/ACCEPTED SS | Поиск | Дети и школьники | Петергоф ... Баллы: списано 20, осталось 63980 из 64000 Доступ есть — можно заливать кампании.

7. Безопасность

  • OAuth-токены хранятся только в зашифрованном виде и никогда не передаются третьим лицам.
  • Все обращения к учётным данным пишутся в журнал доступа.
  • Приложение работает только с теми рекламными аккаунтами, владелец которых явно выдал токен.
  • Данные статистики не публикуются и не передаются за пределы системы.

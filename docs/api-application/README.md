| ---------------------------- | ----------------------------------------- |
| `ads-autopilot-api-spec.pdf` | поле «Спецификации, скриншоты интерфейса» |

Все макеты помечены плашкой «макет интерфейса — не скриншот работающей
системы». Оптимизатор, Telegram-бот и веб-дашборд на момент подачи заявки
находятся в разработке; реально работают валидация конфигурации, генерация
файлов загрузки и `pnpm yd:check`. Выдавать макеты за снимки готового
продукта нельзя — плашка снимает этот вопрос.

## Пересборка

```bash
node docs/api-application/render.mjs
```

Скрипт открывает `spec.html` и `mockups.html` в headless Chromium и
пересобирает PDF и PNG. Правки вносим в HTML, не в картинки.

## Тексты полей заявки

### Какие новые возможности работы с Директом даёт ваше приложение пользователям?

ads-autopilot — серверная система автоматического управления рекламными
кампаниями в Яндекс Директе. Что она даёт помимо интерфейса Директа:

1. Пакетная сборка структуры аккаунта из подготовленной конфигурации:
   кампании, группы, ключевые фразы, объявления, быстрые ссылки и уточнения
   описываются один раз и создаются через API без ручного ввода. Перед
   отправкой всё проверяется на лимиты Директа — длина заголовков и текстов,
   число слов во фразе, дубли фраз между группами, — поэтому заведомо
   некорректные объекты в модерацию не уходят.
2. Ежедневная оптимизация по данным Яндекс Метрики: перераспределение
   недельных бюджетов между кампаниями по фактическому CPA, отключение групп
   и фраз без конверсий, пополнение минус-фраз из отчёта по поисковым
   запросам, чистка неэффективных площадок РСЯ.
3. Контроль модерации: система сама находит отклонённые объявления по
   StatusClarification, переписывает текст и отправляет повторно.
4. Ежедневные отчёты в Telegram: расход, клики, CPL, динамика к прошлой неделе.
5. Human-in-the-loop: изменение бюджета более чем на 20% и остановка кампании
   не применяются автоматически — система запрашивает подтверждение оператора
   в Telegram.

Интерфейс Директа приложение не заменяет: оно снимает массовый ввод
и ежедневные однотипные правки.

### Опишите схему взаимодействия вашего приложения с Директом

Приложение серверное (Node.js на выделенном VPS), веб-интерфейса для
сторонних рекламодателей нет — управление через CLI и Telegram-бота.

Авторизация: OAuth 2.0 Яндекс ID. Токен выдаёт владелец рекламного аккаунта;
токены хранятся в PostgreSQL в зашифрованном виде (AES-256-GCM, ключ
в переменных окружения) и в логи целиком не пишутся. Запросы идут
с заголовками `Authorization: Bearer`, `Accept-Language: ru`.

Используемые сервисы API v5. Чтение: `clients.get`, `campaigns.get`,
`adgroups.get`, `ads.get`, `keywords.get`, `dictionaries.get`, `reports`.
Запись: `campaigns.add/update/suspend/resume`, `adgroups.add/update`,
`ads.add/update`, `keywords.add/update/delete`, `sitelinks.add`,
`adextensions.add`, `audiencetargets.add`, `bids.set`, `keywordbids.set`.

Сценарий 1 — первичная сборка аккаунта, разовая операция по команде
оператора: локальная валидация конфигурации → `campaigns.add` →
`adgroups.add` → `keywords.add` → `ads.add` → `sitelinks.add` /
`adextensions.add` → `campaigns.get` для сверки. Порядка 300 объектов
за прогон, кампании создаются остановленными.

Сценарий 2 — ежедневный цикл оптимизации, один раз в сутки ночью: `reports`
за вчера и за 7 дней плюс отчёт по поисковым запросам → правила выполняются
локально → адресные `update` и `delete`. Порядка 20–50 запросов в сутки
на аккаунт.

Сценарий 3 — контроль модерации, дважды в сутки: `ads.get`
по StatusClarification, отклонённые объявления переписываются
и отправляются через `ads.update`.

Ограничения соблюдаются: не более 5 параллельных запросов на рекламодателя,
объекты передаются пакетами, остаток баллов читается из заголовка `Units`
после каждого ответа и работа останавливается при приближении к суточной
квоте. Ошибка 56 повторяется с экспоненциальной задержкой (до 3 попыток),
152 не повторяется до обновления квоты, 53/54/58 требуют вмешательства
оператора. `RequestId` сохраняется в журнале ошибок.

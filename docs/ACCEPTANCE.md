# Приёмка ТЗ §9.6: трое суток автономной работы

Пункт приёмки звучит так: **«Пройдено 3 полных цикла ежедневной оптимизации без
ручного вмешательства»**. Трое суток настоящего календаря с живыми данными кодом
не заменяются — но решать по памяти и по ощущению через трое суток тоже нельзя.
Здесь записано, что считать циклом, чем это проверять и что делать, если сорвалось.

Команда одна. В дереве исходников:

```bash
pnpm acceptance            # трое последних полных суток по МСК
pnpm acceptance --help     # все ключи
```

На стенде из прод-образа (`pnpm` и `tsx` — dev-зависимости, в образе их нет, см.
[`DEPLOY.md` §6.1](./DEPLOY.md)):

```bash
docker compose -f docker-compose.prod.yml run --rm -e ROLE=acceptance api
docker compose -f docker-compose.prod.yml run --rm -e ROLE=acceptance api --days 1 --telegram
```

Справка это знает сама и печатает ту строку, которой её действительно можно
позвать.

Коды возврата: **0 — пройдено**, **1 — сорвано**, **2 — не хватает улик**.
Третий код отдельный намеренно: «не смог проверить» не должно совпадать ни с
«хорошо», ни с «плохо».

---

## 1. Что такое «полный цикл»

Не пересказ ТЗ, а то, что выводится из кода: суточным считается крон, который
[`CRON_SCHEDULE`](../src/scheduler/schedule.ts) обязывает сработать хотя бы раз в
сутки. Список нигде не набран руками — он вычисляется (`CYCLE_QUEUES` в
[`src/acceptance/spec.ts`](../src/acceptance/spec.ts)), поэтому правка расписания
меняет и определение цикла.

| Крон                 | Расписание МСК | Тиков в сутки | Что делает и чем отчитывается                                  |
| -------------------- | -------------- | ------------: | -------------------------------------------------------------- |
| `fetch-stats-hourly` | `0 * * * *`    |            24 | сущности, статистика, конверсии Метрики; `targets`, `failures` |
| `check-moderation`   | `*/30 * * * *` |            48 | опрос модерации и починка отклонённых; `targets`, `failures`   |
| `pause-losers`       | `0 3 * * *`    |             1 | ночной проход движка правил; `campaigns`, `failed`             |
| `evaluate-ab-tests`  | `0 5 * * *`    |             1 | оценка A/B креативов; `failed`, `approvalsFailed`              |
| `optimize-bids`      | `0 8 * * *`    |             1 | утренний проход движка правил; `campaigns`, `failed`           |
| `daily-report`       | `30 8 * * *`   |             1 | отчёт за вчера в TG; `clients`, `sent`, `failures`             |
| `refresh-tokens`     | `0 */4 * * *`  |             6 | продление токенов кабинетов; `checked`, `failures`             |
| `expire-approvals`   | `*/5 * * * *`  |           288 | просрочка карточек и чистка ключей идемпотентности             |
| `alert-scan`         | `*/5 * * * *`  |           288 | тревоги в TG                                                   |

Не входят и не должны: `weekly-report` (раз в неделю) и `wordstat-mine` (раз в
трое суток) — требовать их внутри суток значит объявлять сорванным каждый вторник.

**Сутки** здесь — календарные сутки работы системы по МСК, а не сутки рекламных
данных. Утренний отчёт внутри этих суток рассказывает про предыдущие: это норма,
а не рассинхрон.

Сутки засчитываются, когда одновременно:

1. каждый крон из таблицы отработал **не меньше положенного числа тиков**;
2. ни одна задача не упала, и внутри сводок нет отказов (`failures`, `failed`,
   `applyFailed`, `approvalsFailed`, `approvalsUndelivered`, `localStateFailed`);
3. работа была **не холостой** — `targets`, `campaigns`, `clients`, `sent`,
   `checked` хоть раз поднялись выше нуля;
4. в `ErrorLog` за эти сутки **пусто**;
5. дневной отчёт **доставлен** — есть `Report.sentAt` внутри суток;
6. ни одной карточки апрува не сорвалось на применении (`decision = FAILED`);
7. никто не запускал команд руками (`AuditLog` с актором вида `cli:*`).

### «Без ручного вмешательства» — что считается вмешательством

**Не считается:** нажатие ✅ или ❌ на карточке апрува в Telegram. Human-in-the-loop
— это штатный ход по ТЗ §3.5, а не поломка автономности; система сама решила
спросить и сама применила ответ. Отчёт такие нажатия показывает отдельной строкой
(«нажатий по карточкам апрува: N»), чтобы человек видел, сколько раз его звали, но
на вердикт они не влияют.

**Считается:** запуск команд руками (`pnpm cli clients`, `pnpm cli credentials`),
правки в базе, ручное изменение в кабинете, перезапуск воркера посреди суток.

### Чего этот признак не ловит — честно

- `pnpm cli optimize --apply` и `pnpm cli ingest`, запущенные руками, ходят в
  кабинет под теми же акторами журнала доступов (`optimizer`, `ingestion`), что и
  крон. В `AuditLog` они от кроновых **неотличимы**. Косвенно они видны по лишним
  строкам в `ChangeLog` без соответствующего прогона — но автоматической проверки
  на это нет. Если во время приёмки такую команду запустили — сутки не в счёт, и
  это на совести человека.
- Перезапуск воркера сам по себе в базе не виден. Виден его след: пропущенные
  тики, и по ним сутки и срываются.
- Клиенты, доступы и кампании считаются **на момент проверки**, а не «какими они
  были в те сутки»: истории статусов система не ведёт.

## 2. Процедура: что делать по дням

### День 0 — запуск стенда

1. Развернуть по [`docs/DEPLOY.md`](./DEPLOY.md). Проверить, что в базе есть
   активный клиент, его доступы и хотя бы одна активная кампания — иначе кроны
   отработают вхолостую и сутки не засчитаются (это и покажет проверка).
2. Убедиться, что воркер поднят и расписания зарегистрированы:

   ```bash
   docker compose logs worker | grep 'scheduled repeatable job'
   ```

   Строк должно быть одиннадцать — по числу очередей с расписанием.

3. Решить про `DRY_RUN`. С `DRY_RUN=true` кроны отработают и отчитаются, но в
   кабинет ничего не уйдёт: проверка такие сутки **засчитает**, потому что со
   стороны расписания они полные. Если приёмка §9.6 понимается как «система
   реально управляла кампаниями», предохранитель надо снимать — это решение
   Романа (CLAUDE.md §10), и оно должно быть принято **до** дня 1, а не после.
4. Сразу поставить проверку в crontab самого стенда, чтобы вердикт приходил в
   Telegram и его не надо было вспоминать (путь — тот же каталог, где лежит
   `docker-compose.prod.yml`; `--no-deps`, чтобы не поднимать одноразовый
   `migrate` каждое утро):

   ```cron
   0 10 * * * cd /root/projects/ads-autopilot && docker compose -f docker-compose.prod.yml run --rm --no-deps -e ROLE=acceptance api --days 1 --telegram >> /var/log/ads-acceptance.log 2>&1
   ```

**День 0 никогда не засчитывается**, и это не придирка: воркер поднялся посреди
суток, часть тиков расписания уже прошла мимо. Первые полные сутки — следующие.

### День 1 — первая проверка

Утром следующего дня — `... -e ROLE=acceptance api --days 1` (дальше по тексту
пишу коротко, `pnpm acceptance`; на стенде подставляй строку из шапки):

```bash
pnpm acceptance --days 1
```

Ожидаемый ответ в первый раз — **НЕТ ДАННЫХ (код 2)**: история очередей ещё не
достаёт до начала проверяемых суток, и проверка отказывается выдавать догадку за
факт. Это нормально. Если вместо этого пришло **СОРВАНО** — читай раздел 3, там
разбор по строкам.

### День 2 — первые настоящие сутки

```bash
pnpm acceptance --days 1
```

Теперь история достаёт до начала суток, и ответ содержательный. Смотреть надо
не на итог, а на строки:

- `✅ fetch-stats-hourly: 24 из 24 тиков` — расписание отработало целиком;
- `❌ … отработало 21 из 24 тиков` — три тика пропали: воркер перезапускали,
  или прогон наложился на предыдущий (тогда рядом будет строка «отложено
  наложением»);
- `❌ … прошло вхолостую: targets ни разу не поднялось выше нуля` — кроны шли,
  но кабинетов у них не было; это не «всё спокойно», а пустой стенд;
- `❓ … история очереди не достаёт до начала суток` — сказать нечего.

### День 3 и день 4 — серия

```bash
pnpm acceptance          # трое суток разом
```

Пункт §9.6 закрыт, когда команда говорит **`ЦИКЛ ТЗ §9.6: ПРОЙДЕН — засчитано
суток 3 из 3`** и возвращает 0. С учётом того, что день 0 не в счёт, на приёмку
уходит **четверо календарных суток**, а не трое.

Вывод команды — приложить к записи в `docs/READINESS.md` целиком, а не пересказом.

## 3. Если сорвалось

Серия обнуляется: трое суток считаются **подряд**. После починки счёт начинается
с первых полных суток после неё.

| Что в отчёте                             | Что это значит                                       | Куда смотреть                                                        |
| ---------------------------------------- | ---------------------------------------------------- | -------------------------------------------------------------------- |
| `N задач упало, первая: …`               | обработчик бросил исключение                         | `docker compose logs worker`, `ErrorLog`                             |
| `отработало N из M тиков`                | воркер лежал, перезапускался или тик не поставился   | `docker compose ps`, аптайм контейнера, [`RUNBOOK.md`](./RUNBOOK.md) |
| `отложено наложением` (в примечаниях)    | прогон не уложился в свой период; следующий тик ушёл | сколько кабинетов, сколько длится прогон в логе `job finished`       |
| `прошло вхолостую: …`                    | кроны идут, работать не с чем                        | активные клиенты, доступы, активные кампании                         |
| `Журнал ошибок: N записей`               | отказ площадки, токена, доставки                     | `ErrorLog` с контекстом; [`RUNBOOK.md`](./RUNBOOK.md)                |
| `Ручное вмешательство: …`                | внутри суток запускали команду                       | `AuditLog`; сутки не в счёт по определению пункта                    |
| `Дневной отчёт доставлен: 0 отчётов`     | отчёт посчитан, но не ушёл                           | `TELEGRAM_BOT_TOKEN`, чат клиента, `ErrorLog` со `scope = reporter`  |
| `расписание не зарегистрировано в Redis` | очередь есть, крона нет                              | лог старта воркера, `upsertJobScheduler` в `src/apps/worker.ts`      |
| `воркер здесь ещё не работал`            | ни расписаний, ни истории                            | воркер не поднимался, либо Redis подняли заново                      |

**Про Redis.** История прогонов живёт в Redis и держится неделю: потолок хранения
считается из периода крона (`jobOptionsFor` в
[`src/scheduler/queues.ts`](../src/scheduler/queues.ts)). Если Redis переподняли
с чистого тома, улики за прошедшие сутки исчезли — проверка скажет «нет данных», и
это правда. Приёмку придётся начинать заново; починить задним числом нечем.

## 4. Ключи команды

```
pnpm acceptance [--days N] [--until YYYY-MM-DD] [--telegram]

  --days N          сколько последних полных суток проверять (по умолчанию 3)
  --until <дата>    последние проверяемые сутки по МСК (по умолчанию вчера)
  --telegram        продублировать вердикт в TELEGRAM_ADMIN_CHAT_ID
```

`--until` нужен для разбора задним числом: `pnpm acceptance --days 1 --until
2026-08-20` покажет те сутки, пока история в Redis до них достаёт.

Проверка **ничего не пишет** — ни в базу, ни в кабинеты, ни в очереди. Запускать
её сколько угодно раз безопасно, в том числе во время работы воркера.

---

## 5. Почему команда, а не крон и не страница дашборда

Крон, который сам о себе отчитывается, — лишний участник в том же процессе, чью
работу он проверяет: упавший воркер промолчал бы и о своём падении. Страницу
дашборда открывают глазами и читают «вроде зелено». Команда возвращает код
возврата, поэтому её читает и человек, и crontab, и она одинаково громко говорит
«ПРОЙДЕН», «СОРВАН» и «НЕТ ДАННЫХ» — а последнее и есть то, чего не умеет ни
таблица, ни память.
